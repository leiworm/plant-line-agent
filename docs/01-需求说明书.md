## 1. 原始需求留档

### 1.1 最初的问题

`【原始】` 做一个工厂的 AI Agent，专门解决**班组长对生产线体的情况掌握**；**用户端只在 Web 上登录操作**。

### 1.2 需求方后续确认的四点

| 编号 | `【原始】` 表述 | 直接推论 |
|---|---|---|
| R-1 | 现场有自己的监控系统，各种 KPI 数据都有 | 数据已存在，Agent 是消费方而非生产方 |
| R-2 | 数据不出工厂，本地有模型 | 私有化 / 本地推理 / 无外网调用 |
| R-3 | 实时异常也是监控系统计算出来的；KPI 有 **UPH、NTF、Retest** | 异常检测不在范围内；三项指标为首批接入对象 |
| R-4 | 无需消息旁路 | 不做企微/钉钉/短信推送，不做移动端 |

### 1.3 关注点

`【原始】` 关注的是 **Agent 的框架怎么设计、由哪些部件组成（子 Agent、SKILL、tool、MCP……）**，而不是数采或前端实现细节。

---

## 2. 需求理解与问题重述

**一句话产品定义** `【细化】`
> 一个部署在厂内的 Web 应用：班组长登录后，用自然语言或快捷按钮，就本班的产线现状、异常、原因和交接班事项提问；系统从既有监控系统取回**已算好的** KPI 与异常事件，做关联与解释，给出**每个数字都能点回原始记录**的回答，并把异常主动推到常开的看板上。

**这件事不是什么** `【补充】`

- 不是新建一套 SCADA / MES，也不是替代现有监控系统；
- 不是自动控制系统，不下发参数、不启停设备、不改工单；
- 不是预测性维护或异常检测算法项目；
- 不是通用聊天机器人，回答必须受限于工具返回的结构化数据。

**价值判据** `【补充】`
> 是否让班组长在**交接班时真的愿意用它**，而不是演示时好看。所有功能以「缩短掌握情况的时间 / 减少漏交接」为唯一衡量方向。

## 3. 完善后的需求

### 3.1 业务目标与成功标准 `【补充】`

| 目标 | 可度量标准（MVP） |
|---|---|
| G-1 缩短掌握现状的时间 | 打开 Web 到看清本班现状 ≤ 10 秒；「现状速览」路径 P95 ≤ 2 秒 |
| G-2 异常不漏 | 监控系统产生的异常事件 100% 在 Web 看板可见（分级节流规则内），端到端 ≤ 5 秒 |
| G-3 结论可信 | 所有数字 100% 可回溯；口径与监控系统一致，偏差为 0（因为不重算） |
| G-4 交接班不漏项 | 交接班草稿必填项完整率 100%，人工确认后归档 |
| G-5 真实使用 | 试用产线连续 5 个班次的交接班实际使用，班组长满意度问卷 ≥ 4/5 |

### 3.2 用户与角色 `【补充】`

| 角色 | 主要动作 | 数据可见范围 |
|---|---|---|
| **班组长（主用户）** | 总览、问答、异常卡片处置、交接班确认 | 仅本人负责的 `line_id`（可配置跨线只读） |
| 设备 / 工艺工程师（次要） | 查归因、查历史案例、核对口径 | 授权线体，只读 |
| 生产主管（次要） | 跨线对比、看归档交接班 | 所辖车间全部线体，只读 |
| 系统管理员 | 后台配置口径版本、权限、知识库、订阅规则 | 配置数据；**不因角色获得额外产线数据** |

`【补充】` **登录与权限**：接入厂内 SSO / LDAP；权限过滤在 MCP Server 内按登录态执行，**不允许靠提示词约束**；越权 `line_id` 返回空结果并记录审计。

### 3.3 场景清单与优先级 `【细化】`

| ID | 类别 | 班组长典型问法 | 优先级 | 说明 |
|---|---|---|---|---|
| S-1 | 现状 | 「3 号线现在怎么样」「本班产量 vs 计划」 | **P0 / MVP** | 路径固定 → 走工作流 |
| S-2 | 现状 | 「这一班 UPH / NTF / Retest 多少，跟上一班比呢」 | **P0 / MVP** | 数值比较交给工具 |
| S-3 | 异常 | 「哪台停了、停多久、什么代码、有没有没闭环的安灯」 | **P0 / MVP** | 直接取监控系统事件 |
| S-4 | 异常 | 「刚才那条异常现在什么状态」 | P0 | 事件卡片详情 |
| S-5 | 归因 | 「为什么 NTF 升高 / 为什么这条线慢」 | P1 | 唯一需要多步检索，走归因子 Agent |
| S-6 | 处置 | 「按 SOP 该找谁、先查哪一步」 | P1 | 检索本地 SOP，**只给建议不执行** |
| S-7 | 复盘 | 「生成本班交接班小结」「有哪些遗留问题」 | P1（班后定时） | 草稿 + 人工确认 |
| S-8 | 对比 | 「跟上周 / 其他线比如何」 | P2 | 需跨班次口径版本一致后才开放 |
| S-9 | 预测 | 「照这个趋势会不会出问题」 | **不做** | 超出「已有 KPI」范围，易产生不可验证结论 |

`【修正】` 原始需求未区分场景优先级。建议 **MVP 只做 S-1 ~ S-4**，并且**只回答可被数据验证的问题**：不做预测、不给「建议调参数」、不下控制指令。

### 3.4 功能性需求 `【细化/补充】`

| ID | 需求 | 优先级 | 验收要点 |
|---|---|---|---|
| FR-01 | Web 单一入口：登录、总览、问答、异常卡片、交接班、后台 | P0 | 不安装任何客户端/插件；工位机与平板浏览器可用 |
| FR-02 | 一屏总览：按红/黄/绿展示所辖线体当前状态与本班 KPI | P0 | 刷新间隔可配，数据带最后更新时间 |
| FR-03 | 快捷问题按钮（现状、异常、对比、交接班）+ 自由文本提问 | P0 | 快捷按钮走工作流，自由文本走主 Agent 路由 |
| FR-04 | 回答中每个数字可点击展开：`source`、`timestamp`、`metric_version`、监控系统原始记录链接 | P0 | 无来源的数字禁止输出 |
| FR-05 | 异常事件订阅 → 去重 → 分级 → 节流 → 站内 WebSocket/SSE 推卡片 | P0 | 卡片不依赖 LLM 即可生成；LLM 只补一句解释 |
| FR-06 | 异常卡片可记录处置状态与备注（**仅在本系统内**，不回写监控系统） | P1 | 需人工确认；写操作留审计 |
| FR-07 | 归因问答：关联趋势、测试明细、工单、维修史、历史案例、SOP | P1 | 输出「可能原因 + 证据 + 建议 + 不确定项」四段式 |
| FR-08 | 班前简报 / 班后交接班草稿，可编辑、确认、归档、查历史 | P1 | 必填项缺失时不允许确认归档 |
| FR-09 | 后台：口径版本、线体授权、订阅规则、知识库维护、审计查询 | P1 | 口径变更留版本与时间 |
| FR-10 | 数据不可用时降级显示「数据源不可用，最后更新 xx」 | P0 | 不使用缓存值冒充实时、不补全 |
| FR-11 | 全程只读（一期）：MCP Server 不暴露任何写/控制类工具 | P0 | 工具清单白名单可审计 |
| FR-12 | 口径变更时，跨版本对比自动加提示或禁用 | P2 | 避免不同口径的历史数据被直接比较 |
| FR-13 | 厂内黑话 / 别名 / 事件码映射到标准 ID | P1 | 由 `plant-terms` 技能维护 |

### 3.5 数据契约与口径 `【补充】`（本项目的核心需求）

1. **Agent 不计算 KPI**。UPH、NTF、Retest、环比、达成率、排名等全部由监控系统或确定性工具返回；模型只做选择、组织与措辞。
2. 每个工具返回体统一包含：

```json
{
  "data": { "...": "业务字段" },
  "source": "monitoring-system://kpi/snapshot",
  "timestamp": "2026-11-11T22:30:00+08:00",
  "metric_version": "kpi-2026.11",
  "status": "ok | stale | unavailable"
}
```

3. `status != ok` 时，Agent 必须按 `evidence-rules` 输出降级说明，**禁止编造数值或用历史值填充**。
4. 每条数据必须能定位到 `line_id` / `shift_id` / `sku` / `work_order_id` / `equipment_id`（按数据种类适用）。
5. **口径版本化**：UPH / NTF / Retest 的定义、统计窗口、目标值、阈值由生产 + 设备 + IE 三方确认后写入 `kpi-glossary` 技能与 `metric_version` 配置，变更留版本。

`【假设】` 口径占位（**待三方签字，不得直接投产**）：

| 指标 | 暂定含义 | 统计窗口 | 目标值 | 阈值来源 |
|---|---|---|---|---|
| UPH | Units Per Hour，单位小时产出 | 当前班次累计 | 由排产计划给定 | 监控系统 |
| NTF | No Trouble Found，送修/复测未复现比例 | 当前班次累计 | 待确认 | 监控系统 |
| Retest | 复测率 / 复测台数占比 | 当前班次累计 | 待确认 | 监控系统 |

> `【待确认】` 三项指标的确切定义、分子分母、是否含返工、统计窗口边界（跨班次如何归属）必须以监控系统报表口径为准，逐条对齐后再写死。

### 3.6 非功能性需求 `【补充】`

| 类别 | 要求 |
|---|---|
| **部署** | 全链路厂内：本地 LLM、向量库、审计库、应用服务、Web 均不出厂；无外网调用；无第三方遥测 |
| **性能** | 现状速览 / KPI 问答 P95 ≤ 2 s；归因问答 P95 ≤ 15 s；异常事件到卡片 ≤ 5 s；Web 首屏 ≤ 3 s |
| **容量** | 以「1 条试点线 × 3 班 × 并发 20 用户」为 MVP 基线；事件风暴（如 100 事件/分钟）不拖垮页面 |
| **可靠性** | 监控系统不可用时 Web 仍可登录并显示降级态；事件订阅支持断线重连、断点回放；服务重启不丢未归档草稿 |
| **安全** | SSO 登录；线体级数据隔离；MCP 工具只读白名单；参数校验；OT/IT 网络隔离，Agent 不直连控制网/数据库 |
| **可追溯** | 全量审计：每次问答、每次工具调用（入参/出参摘要/耗时）、每次写操作、每次口径变更，保留期按厂内规定 |
| **可维护** | 口径、黑话、简报格式放 SKILL（改文本即可生效）；监控系统接口变化只改 MCP Server，Agent 框架不动 |
| **兼容性** | Chrome / Edge 近两个大版本；适配工位机 1920×1080 与平板横屏；不依赖浏览器插件 |
| **可用性** | 界面以卡片 + 大按钮为主，避免要求班组长学会写提示词；术语用厂内习惯叫法 |

### 3.7 约束与范围边界 `【补充】`

**必须遵守**：只读 · 数据不出厂 · Web 唯一入口 · 无消息旁路 · 复用既有 KPI 与异常结果。

**明确排除（一期）**：

- 数采 / 边缘网关 / 点位映射 / PLC 直连；
- KPI 重算、异常检测、预测、参数优化建议；
- 任何写工具、设备控制、参数下发、工单回写；
- 企微 / 钉钉 / 短信 / 邮件 / 移动端推送；
- 多 Agent 投票、自我反思循环等重型编排；
- 公网模型 API、公有云向量库、第三方 SaaS。

`【补充】` **已接受的取舍**：只在 Web 操作且无消息旁路 ⇒ **人离开浏览器就收不到主动告警**。方案以「常开看板页 + 浏览器通知」缓解，但不消除该限制。若未来允许「仅提醒、不操作」的旁路，架构中预留 `events/notification_adapter` 扩展位，不改主路径。

### 3.8 验收标准（AC） `【补充】`

| AC | 标准 | 验证方式 |
|---|---|---|
| AC-1 | Agent 输出的 UPH/NTF/Retest 与同一时刻监控系统报表**完全一致** | 抽 30 个时间点逐项比对 |
| AC-2 | 回答中 100% 的数字可点击回溯到原始记录（含 source / timestamp / metric_version） | 自动化遍历问答结果 |
| AC-3 | 断开源数据 30 秒，页面显示降级提示且**不出现任何数值** | 故障注入 |
| AC-4 | 班组长 A 请求未授权 `line_id`，返回空结果并生成审计记录 | 越权用例 |
| AC-5 | 注入 3 分钟内 100 条同类事件，页面只出现符合节流规则的卡片，无重复、无卡死 | 事件风暴用例 |
| AC-6 | 现状速览 P95 ≤ 2 s，归因问答 P95 ≤ 15 s | 压测 100 次 |
| AC-7 | 交接班草稿必填项缺失时无法归档；归档后可查历史 | 功能用例 |
| AC-8 | 口径版本变更后，跨版本对比被提示或禁用 | 配置变更用例 |
| AC-9 | 工具清单中不存在任何写/控制类工具 | 白名单审查 |
| AC-10 | 试点线连续 5 个班次交接班实际使用 | 现场试用 |

## 4. 相对原始需求的修改清单（本次完善内容）

> 这一节是「帮你修改完善需求」的落点，请逐条确认或驳回。

| # | 类型 | 内容 | 理由 |
|---|---|---|---|
| M-01 | **修正** | 把「掌握产线情况」从目标改写为 6 类可回答的问题，MVP 只做现状 + 异常（可被数据验证） | 「掌握情况」无法验收；开放归因易产生不可验证结论 |
| M-02 | **修正** | 明确 **Agent 不重算 KPI、不二次判定异常**，只做取数/关联/解释 | 既有监控系统已是唯一事实源；两套口径会互相矛盾 |
| M-03 | **补充** | 数据契约：所有返回体带 `source`/`timestamp`/`metric_version`/`status` | 工业场景结论必须可追溯，是可信的前提 |
| M-04 | **补充** | 口径版本化 + 三方签字；口径放 SKILL 而非代码 | 口径变更是常态，改代码代价高且跨班次对比会失真 |
| M-05 | **补充** | 角色与线体级数据隔离，权限在 MCP Server 执行 | 原需求只说「Web 登录」，未定义谁能看哪些线 |
| M-06 | **补充** | 非功能需求（响应时延、降级、审计、事件风暴、兼容性） | 原需求未涉及，但决定现场能不能用 |
| M-07 | **补充** | 量化验收标准 AC-1 ~ AC-10 | 让「做完了」有客观判据 |
| M-08 | **细化** | 三条独立运行路径（对话 / 事件 / 定时），事件卡片不依赖 LLM | 原需求隐含「异常要主动知道」，但纯 Web 无旁路，必须站内推 |
| M-09 | **补充** | 明确排除项：写操作、设备控制、参数下发、外部通知、预测、数采 | 防止范围蔓延，尤其避免「让 Agent 控产线」 |
| M-10 | **补充** | 明确记录「离屏即失联」为已接受取舍，并预留扩展位 | 纯 Web 约束的必然代价，需需求方知情 |
| M-11 | **假设** | NTF = No Trouble Found；三项口径先占位 | 需要业务方确认，未确认前不得投产 |
| M-12 | **补充** | 把「关注框架设计」落成部件级交付物（Agent/SKILL/MCP 定义 + 配置骨架） | 让框架可被评审、可被逐件实现 |

| 术语 | 含义 |
|---|---|
| SKILL | 给 AI 的可复用操作说明书（`SKILL.md` + 可选附件），按需自动加载，管「怎么做、何时用」 |
| Tool | 单个确定性动作（查 KPI、查事件…），输入输出 schema 固定，是 AI 唯一的「手」 |
| MCP | 把一组 Tool 以统一协议接入 Agent 的适配层；本项目中同时承担鉴权、审计、限流收口 |
| Agent | 带判断力的执行角色；本项目 1 主 + 2 子 |
| 工作流 | 路径预先确定的固定流程（调工具 → 套模板 → 输出），不经 LLM 规划，快且稳 |
| 主 Agent（Router） | 只做意图分类、路径选择、答案组装与证据检查，不做数值计算 |
| 证据链 | 数字 → 原始记录的可点击追溯路径，含来源、时间戳、口径版本 |
| 降级 | 数据源异常时明确告知不可用，而非给出看起来合理的数值 |
| UPH / NTF / Retest | 既有监控系统产出的三项 KPI，定义以监控系统为准 |
